# 17 - 게스트 2명 중 한 명만 궤적이 안 생기던 문제

## 증상 (정현 보고)
> 게스트 1명은 정상. 게스트 2명이 되면 한 명은 궤적·점령 정상, 다른 한 명은 궤적이 안 만들어짐.

---

## 먼저 — 지목된 곳은 원인이 아니었다

지시하신 네 가지를 먼저 다 확인했다. **네 가지 모두 이미 정상이다.**

| 확인 항목 | 결과 |
| --- | --- |
| 1. 방장 루프가 게스트 전원을 도는가 | **정상.** `stepMatch()`는 `for (const e of ents)`로 전원을 돈다. 한 명만 처리하는 코드는 없다 |
| 2. 참가자마다 `gx`/`gz`를 따로 갖는가 | **정상.** `makeEnt()`가 참가자별로 새 객체를 만든다. 공유·덮어쓰기 없음 |
| 3. `applyInput`의 netId 매핑이 게스트마다 다른 ent로 가는가 | **정상.** 실측에서 세 명의 netId가 전부 달랐고 각자 다른 ent로 갔다 |
| 4. 4인(게스트 3명) | **정상.** 넷 다 똑같이 457칸씩 점령했다 |

`index.html`의 게임 로직을 그대로 떼어 내 **방장 1 + 게스트 2·3을 한 프로세스에서
각각 독립 모듈로 띄우고** relay를 그대로 흉내 내 돌렸다. 12초·30초 두 시점에서
방장 격자와 게스트 격자를 칸 단위로 비교한 결과 **다른 칸 0개**다.
```
[12초] 방장 궤적 {"1":46,"2":46,"3":46,"4":46}
       게스트1 {"1":46,"2":46,"3":46,"4":46} · 다른칸 궤적 0 소유 0
       게스트2 {"1":46,"2":46,"3":46,"4":46} · 다른칸 궤적 0 소유 0
       게스트3 {"1":46,"2":46,"3":46,"4":46} · 다른칸 궤적 0 소유 0
```

## 진짜 원인 — 게스트의 위치 보고가 포인터 잠금에 묶여 있었다

루프는 이랬다.
```js
if (iamHost) hostTick(now); else if (locked) guestTick(now);
```
`locked`는 **내 창의 마우스 포인터 잠금** 여부다. 다른 창을 클릭하거나 ESC를 누르면
브라우저가 자동으로 푼다. 그리고 **[참가하기]를 아직 안 누른 게스트도 `locked`가 거짓이다.**

잠금이 풀린 게스트는 `guestTick()`이 통째로 안 돌아 **방장에게 아무것도 못 보낸다.**
방장은 그 사람을 시작 칸에 세워 둔 채로 판단하므로 **궤적이 한 칸도 안 생기고 점령도 없다.**
반면 잠금을 쥔 게스트는 멀쩡하다. 딱 보고된 그림이다.

### 왜 게스트가 2명이 되면 티가 나나
**한 PC에서 탭·창을 여러 개 띄워 시험하기 때문이다.** 포인터 잠금은 포커스를 쥔 창
하나만 가질 수 있다. 게스트1 창을 클릭해 조작하는 순간 게스트2 창의 잠금은 풀린다.
게스트가 1명일 때는 늘 그 창을 보고 있으니 드러나지 않는다.

### 시뮬레이터로 재현
게스트2만 위치 보고를 끊었더니 그대로 나왔다.
```
방장     점령완료 1회 · 최대궤적 99칸
게스트1   점령완료 1회 · 최대궤적 99칸
게스트2   점령완료 0회 · 최대궤적  0칸     ← 증상
```

## 덤으로 찾은 두 번째 결함 — 리스폰 직후 없는 궤적이 그어진다

방장이 게스트를 죽이고 1.5초 뒤 시작 칸에 되살린다. 그런데 게스트는 **자기가 되살아난 걸
모르고 죽은 자리 좌표를 계속 보내고**, 방장은 그걸 그대로 받아 **시작 칸에서 죽은 자리까지
선을 긋는다.** 아무도 걷지 않은 궤적이다.

측정값 — 게스트를 (76,172)에서 죽이고 리스폰시킨 직후:
```
13.60초  방장이 본 게스트1: 칸(74,176) 궤적 51칸    ← 되살아나자마자 51칸
```
게다가 **죽어 있는 동안 게스트가 계속 걸어 다니고 있었다.** `movePlayer()`가 생사와
무관하게 돌기 때문이다. 그래서 어긋남이 더 벌어졌다.

## 고친 내용

| # | 고친 것 | 이유 |
| --- | --- | --- |
| 1 | **게스트는 잠금과 무관하게 위치를 보고한다** | 방장이 "가만히 서 있는 사람"을 실제로 보게 한다 |
| 2 | **보고에 `r`(조작 가능 여부)를 실어 보낸다** | 방장이 "서 있는 사람"과 "아직 못 들어온 사람"을 구분한다 |
| 3 | **`조작 대기 중 — 화면을 클릭해야 움직입니다`를 킬로그에 띄운다** | 원인이 안 보이면 정상 동작도 버그로 보인다 (07 문서와 같은 판단) |
| 4 | **리스폰 직후 2초간은 리스폰 칸 근처(3칸 이내) 보고만 받는다** | 없는 궤적이 그어지는 걸 막는다 |
| 5 | **보고에 `n`(내가 아는 내 사망 횟수)을 실어 죽기 전 좌표를 버린다** | 위와 같은 이유. 두 겹으로 막는다 |
| 6 | **죽어 있는 동안에는 못 움직인다** | 시신이 걸어다니면 리스폰 자리와 어긋난다. 오프라인에도 같이 적용 |
| 7 | **게스트는 되살아날 때도 방장이 찍어 준 자리로 옮겨간다** | 전에는 사망 횟수가 바뀔 때만 옮겼다 |
| 8 | 온라인 판정의 시계를 루프가 주는 시각 하나로 통일 | `performance.now()`와 섞어 쓰면 판정이 깜빡인다 |

```js
// 게스트가 보내는 것
send({ t: 'relay', data: { k: 'i', n: me.deaths, r: locked ? 1 : 0, x, z } });

// 방장이 받는 것
if (d.n !== undefined && d.n !== e.deaths) return;        // 죽기 전 좌표 — 버린다
if (e.warpT && netNow < e.warpT) {                        // 방금 리스폰시켰다
  if (|보고 칸 - 리스폰 칸| > 3) return;                   // 아직 옛 자리다 — 기다린다
  e.warpT = 0;
}
```

## 검증

### (1) 실제 서버 + 실제 브라우저 3대 (방장 + 게스트 2)
프로덕션(5002)은 건드리지 않고 **사본을 5099에 따로 띄워** 헤드리스 크롬 3대를 붙였다.
```
방 생성 → 게스트 2명 입장 → 경기 시작 → 각자 20칸 네모를 그린다
```
| 클라이언트 | 자기 netId | 세 사람 점령 칸 | 세 화면의 격자 |
| --- | --- | --- | --- |
| 방장 | 83f069d7 | 457 / 457 / 457 | 동일 |
| 게스트1 | 00337314 | 457 / 457 / 457 | 동일 |
| 게스트2 | e7b57f32 | 457 / 457 / 457 | 동일 |

**게스트 둘 다 궤적이 생기고 똑같이 점령한다.** 런타임 오류 0건.

### (2) 실제 브라우저 4대 (방장 + 게스트 3)
```
ents: [1 9a84c4ae 457] [2 bb3b2558 457] [3 77720054 457] [4 e46d48c0 457]
격자소유(네 화면 모두): {"1":457,"2":457,"3":457,"4":457}
```
netId 네 개가 전부 다르고, 넷 다 똑같이 점령한다. 서로 덮어쓰지 않는다.

### (3) 화면을 클릭하지 않은 게스트 — 이유가 보이는가
게스트2만 포인터 잠금을 걸지 않은 상태로 같은 시험을 돌렸다.
```
격자소유: {"1":457, "2":25, "3":457}         ← 게스트2는 시작 블록 25칸 그대로
피드(세 화면 모두): "플레이어-2987 — 조작 대기 중 — 화면을 클릭해야 움직입니다"
```
**못 움직이는 건 그대로지만(입력이 안 들어오니 당연하다), 왜 그런지가 전원 화면에 뜬다.**
전에는 아무 설명 없이 그 사람만 궤적이 없었다.

### (4) 리스폰 직후 가짜 궤적

| --- | --- | --- |
| 되살아난 직후 궤적 | **51칸** (시작 칸 → 죽은 자리) | **0칸** |
| 되살아난 위치 | (74,176) — 죽은 자리 근처 | (53,147) — 자기 영역 안 |

## 알려진 이슈
1. **창이 뒤로 밀린 게스트는 여전히 못 움직인다.** 키 입력이 그 창으로 안 가고 포인터 잠금도
   풀리므로 코드로 해결할 수 없다. 이번 수정은 **왜 그런지를 보이게** 한 것이다.
   여러 명 시험은 **창을 따로 띄워 나란히 놓고** 하시길 권한다.
2. **탭을 완전히 뒤로 숨기면** 브라우저가 화면 갱신을 초당 1회로 낮춰 보고도 그만큼 느려진다
   (12 문서와 같은 제약).
3. 14·16 문서의 온라인 밸런스 건(무제한 궤적, 숨어 기다리기)은 방침 대기 중이다.

## 감독 확인 요청
1. **창 3~4개를 나란히 띄워 붙어 주시고, 게스트 전원 궤적이 나오는지** 봐주시면 좋겠다.
2. 조작을 안 하고 있는 사람이 있으면 **킬로그에 "조작 대기 중"이 뜨는지** 같이 봐주시면 좋겠다.
3. 죽고 되살아난 뒤 **엉뚱한 곳까지 선이 그어지지 않는지**도 확인 부탁드린다.
