## 동기화 구조

### 역할
```
게스트 ──{k:'i'} 내 위치──▶ 서버(중계) ──▶ 방장
방장 ──{k:'s'} 상태 스냅샷──▶ 서버(중계) ──▶ 게스트 전원
```
- **방장이 유일한 판정자**다. 궤적·점령·죽음·리스폰·타이머·점유율을 전부 방장이 계산한다.
- 게스트는 **자기 이동만 로컬에서 처리**하고(반응성) 그 위치를 방장에게 올린다.
  방장은 그 위치를 그대로 믿고 격자 판정을 돌린다 (캐주얼 기준, 치팅 방지는 범위 밖).
- 서버는 `relay` 로 내용을 보지 않고 넘긴다. 08단계에서 잡아둔 통로를 그대로 쓴다.

### 주기와 전송량
| 항목 | 값 | 이유 |
| --- | --- | --- |
| 틱 | **55ms (약 18Hz)** | 지시 범위(15~20Hz) 안. 정확성 우선이라 보간·예측은 넣지 않았다 |
| 위치 정밀도 | 0.05m 로 반올림 | 문자열 길이를 줄인다. 셀 크기 1.5m라 판정에 영향 없다 |
| 셀 전송 | 변경분만, 한 틱당 **최대 2,500칸** | 4만 칸 전체를 보내면 매 틱 수백KB가 된다 |

**셀 변경분 전송이 핵심이다.** `paint()` 가 바뀐 칸 번호를 `dirtySet` 에 모으고, 방장이 틱마다 꺼내
`[칸번호, 값]` 쌍으로 보낸다. 값은 `owner | (trail << 3)` 로 한 바이트에 담는다.
큰 점령(수천 칸)은 여러 틱에 나눠 흘러간다 — 그래서 검증 로그에서 점령 직후 한두 번 격자합이
어긋났다가 곧 일치로 돌아온다. **최종 상태는 항상 수렴한다.**

### 스냅샷 내용
```js
{ k:'s', t: 남은시간,
  e: [[슬롯, x, z, 생존, 점유칸수, 사망횟수], ...],
  c: [칸번호, 값, 칸번호, 값, ...],       // 변경된 칸만
  f: [[슬롯, '사유'], ...] }              // 킬로그 (있을 때만)
```
- **사망횟수**가 게스트의 리스폰 신호다. 내 사망횟수가 늘면 방장이 준 좌표로 순간이동한다.
  그 외에는 게스트가 자기 위치의 주인이다.
- 궤적 벽(3D)은 참가자별 배열이 아니라 **격자를 직접 훑어** 만든다. 게스트에는 궤적 배열이 없기 때문이다.

### 시작 · 종료
- 방장 `start_game` → 서버가 `game_start{room, members}` 를 방 전원에게 → 전원이 같은 인원·같은 설정으로
  `initMatch()` 를 돌린다. **시작 배치는 인원 수만으로 정해지므로 누가 계산해도 같다.**
- 종료는 방장이 판정하고 `{k:'e'}` + `end_game` 을 보낸다. 게스트는 마지막 상태를 반영한 뒤 순위표를 띄운다.
- 제한시간·승리 점령률은 **방 설정값**을 그대로 쓴다 (60~300초, 60% 또는 없음).

### 이탈 처리
| 상황 | 처리 |
| --- | --- |
| 게스트 이탈 | 해당 참가자를 사망 처리하고 궤적을 지운다. 킬로그에 `접속 종료`. 경기는 계속된다 |
| 방장 이탈 | 계산 주체가 사라진다 → **그 시점 성적으로 경기를 끝낸다.** 서버는 남은 사람에게 방장을 위임한다 |
| 연결 끊김 | 08단계의 자동 재접속(1→2→4→8초)이 돈다. 경기 중이면 로비로 돌아간다 |
| 정원 미달 | 서버가 방을 `진행` 에서 `대기` 로 되돌린다 |

## 밸런스 — "외곽 한 바퀴 즉시 100%" 봉쇄

### 채택: 궤적 길이 상한 (`TRAIL_CAP = 320칸 = 480m`)
자기 영역 밖에 있는 동안 그린 궤적이 320칸을 넘으면 **그 자리에서 끊어져 죽는다.**
HUD에 70% 넘으면 `궤적 224/320 위험` 이 뜬다.

### 왜 이 방식인가
지시에 있던 **"가장자리 한 겹 점령 불가"는 이 문제를 못 막는다.** 점령은 바깥 테두리에서
flood-fill 해서 "바깥과 안 이어진 칸"을 먹는 방식이라, 테두리 한 겹을 못 먹게 해도
그 **바로 안쪽으로 한 바퀴 돌면 나머지 전부가 갇힌다.** 테두리만 남고 99%를 먹는다.
반면 길이 상한은 **폐곡선의 둘레 자체를 제한**하므로 우회가 없다.

### 수치 근거
| 항목 | 계산 | 결과 |
| --- | --- | --- |
| 맵 | 300m × 300m | 90,000 m² |
| 맵 외곽 한 바퀴 | (300+300)×2 = 1,200m = **800칸** | 상한 320칸의 2.5배 → **불가능** |
| 상한 480m 폐곡선의 최대 면적 | 원일 때 P²/4π = 480²/4π | 18,335 m² = **20.4%** |
| 같은 둘레, 정사각형일 때 | (480/4)² | 14,400 m² = **16%** |

즉 **한 번의 외출로 최대 20%**까지만 먹을 수 있다. 100%를 먹으려면 최소 다섯 번은 나갔다 와야 하고,
그 사이 상대에게 궤적을 잘릴 기회가 생긴다. 봇의 기존 상한(220칸)은 이보다 낮아 영향이 없다.

## 동작 검증 (실서버·실터널 경유, 헤드리스 크롬 다중 탭)
격자 전체를 해시한 값을 각 탭에서 뽑아 **전 참가자의 격자가 같은지** 직접 비교했다.

**4인 · 1분 — 끝까지 완주**
```
[  7s] game  시계 58  격자합 전원 일치   25 | 25 | 25 | 25칸
[ 28s] game  시계 43  격자합 2종         25 | 25 | 25 | 676칸     ← 점령 직후, 델타 전송 중
[ 35s] game  시계 37  격자합 전원 일치  367 | 458 | 562 | 678칸
[ 70s] game  시계  5  격자합 전원 일치  367 | 460 | 566 | 680칸
[ 77s] result 시계 0  격자합 전원 일치  367 | 460 | 567 | 681칸  ← 전원 동시 종료
순위표(P1) 1.플레이어-2496 1.7% / 2.플레이어-2472 1.4% / 3.플레이어-8369 1.1% / 4.플레이어-4618 0.9%
순위표(P3) (동일)
```

**3인** — 시작·동기화 정상, 격자합 수렴 확인.
**2인** — 시계 오차 0~1초, 격자합 수렴, 점령 수치 양쪽 동일.

**화면** — 게스트 화면에 상대 영역·궤적·미니맵 양쪽 표시 확인. 결과 화면에 4명 순위·색·본인 강조,
온라인일 때 버튼이 `방 나가기` 로 바뀌는 것까지 확인.

**검증 중 잡은 버그 1개** — 참가자가 4명 미만이면 몸체 메시 슬롯이 비는데 그걸 그대로 읽어
`Cannot read properties of undefined (reading 'alive')` 로 게스트 화면이 죽었다. 빈 슬롯 방어를 넣었고,
소유자 id로 참가자를 찾는 다른 세 곳에도 같은 방어를 추가했다.

**자동 검증의 한계** — 헤드리스 크롬은 포인터 잠금을 허용하지 않아 **걷기 조작만** 함수 호출로 대체했다
(각 탭이 자기 집 주변을 원으로 돈다). 네트워크·판정·렌더·종료는 전부 실제 코드 경로다.

## 알려진 버그 · 미완
1. **보간 없음.** 상대 캐릭터가 18Hz로 툭툭 움직인다. 지시대로 정확성을 택한 결과다.
   부드럽게 하려면 위치 보간을 넣어야 한다.
2. **치팅 방지 없음.** 방장이 게스트가 보낸 위치를 그대로 믿는다. 속도 검사조차 없다.
3. **방장 이탈 = 경기 종료.** 이어받기(state handoff)는 없다.
4. **점령 직후 1~2틱 동안 게스트 화면이 살짝 뒤처진다.** 큰 점령이 여러 틱에 나눠 가기 때문이다.
5. **자동 기동 여전히 미적용** — 재부팅하면 WS 서버와 터널이 죽는다 (`server/install_autostart.sh` 대기 중).
6. 인증 없음, 방 목록 상한 6개, 재접속 시 방 자동 복귀 없음 (08 문서 그대로).

## 감독 확인 요청 사항
1. **두 기기(또는 두 탭)로 직접 대전 확인 부탁드린다.** 걷기 조작만 자동 검증이 안 됐다.
2. **궤적 상한 320칸(480m)이 적절한지** 체감으로 판단 바란다. 짧으면 답답하고, 길면 한 방 점령이 커진다.
3. **승리 점령률 60%는 여전히 높다.** 한 번에 최대 20%라 3분 안에는 사실상 불가능하다.
   20~30%로 낮추거나 방 설정 선택지를 늘리는 편이 낫다.
4. **자동 기동 등록 여부** (08 문서에서 이월).
