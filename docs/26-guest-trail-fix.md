# 26 - 온라인 상대 궤적·점령 안 됨 (stepCells 순간이동 분기)

## 증상 (정현 보고)
> 방 만들어 상대방(게스트)이 들어오면 상대 궤적이 안 그려지고 점령이 안 된다.

## 원인 — 한 줄이 두 줄을 잡아먹었다

`stepCells()`의 순간이동 분기가 `ent.gx/gz`를 **새 칸으로 먼저 갱신한 뒤** `stepCell()`을 불렀다.
```js
if (Math.abs(gx - cx) + Math.abs(gz - cz) > 64) {   // 순간이동(리스폰 등)은 잇지 않는다
  ent.gx = gx; ent.gz = gz;        // ← 먼저 갱신
  stepCell(ent, gx, gz);           // ← 아래 첫 줄에 걸려 즉시 return
  return;
}
```
`stepCell()`의 둘째 줄이 "같은 칸이면 할 일 없다"는 가드다.
```js
function stepCell(ent, gx, gz) {
  if (!inGrid(gx, gz)) return;
  if (gx === ent.gx && gz === ent.gz) return;      // ← 방금 맞춰 놨으니 100% 걸린다
```
그래서 **그 칸의 판정이 통째로 빠졌다.**

| stepCell 이 하는 일 | 순간이동 분기에서 |
| --- | --- |
| `takeItem()` 아이템 줍기 | **안 됨** |
| `trail[i] = ent.id` 궤적 찍기 | **안 됨** |
| `owner[i] === ent.id` → `capture()` 집 복귀 점령 | **안 됨** |
| 남의 궤적 밟음 / 자기 궤적 밟음 판정 | **안 됨** |

좌표(`ent.x/z`)만 움직이고 격자 판정이 없으니, **보는 쪽에서는 상대가 미끄러져 다니기만 하고
선이 안 생기고 땅도 안 늘어난다.**

### 왜 온라인에서만 터졌나
- **봇전**: 봇은 매 프레임 한 칸씩 간다. 델타가 1~2칸이라 이 분기를 거의 안 탄다.
- **온라인**: 격자가 200칸이고 시작 칸이 100칸씩 떨어져 있다. 게스트 참가 직후·리스폰 직후·
  지연이 끼면 **64칸을 넘는 점프가 흔하다.** 특히 17 문서에서 게스트가 포인터 잠금 전에는
  위치를 안 보내게 바꾼 뒤로 첫 보고가 늦게·멀리서 오는 일이 더 잦아졌다.
- 집으로 돌아오는 마지막 보고가 64칸을 넘으면 **점령 자체가 날아간다.** 이게 "점령이 안 된다"다.

## 수정
```js
    // 이전 칸을 지운 뒤 넘긴다. 여기서 ent.gx/gz 를 새 칸으로 '먼저' 갱신하면
    // stepCell 첫 줄의 `gx === ent.gx && gz === ent.gz` 에 걸려 즉시 return 하고,
    // 그 칸의 궤적 찍기·집 복귀 capture·아이템 줍기가 통째로 빠진다 (26 문서).
    // 위 `ent.gx < 0` 분기와 같은 뜻 — 이어 붙일 이전 칸이 없다는 표시다.
    ent.gx = -1; ent.gz = -1;
    stepCell(ent, gx, gz);
```
**두 글자다.** `gx, gz` → `-1, -1`. 바로 위 `if (ent.gx < 0)` 분기와 같은 관례를 쓴다 —
"이어 붙일 이전 칸이 없다". `stepCell()`이 841줄에서 `ent.gx/gz`를 새 칸으로 제대로 세팅하므로
`-1`이 남는 경우는 없다 (`inGrid`는 `stepCells` 첫 줄에서 이미 통과했다).

## 검증 — 헤드리스 크롬 다중 탭 + CDP

측정은 **수정 전(HEAD `1ea345c`)과 수정 후를 같은 시나리오로** 돌렸다.
게스트의 `pos`를 격자 칸으로 옮기면 `guestTick()`이 그 좌표를 방장에게 보고하므로,
실제 경로를 그대로 재현할 수 있다.

### (1) 수정 전 — 버그 재현
게스트 시작 칸 `[150,50]` → `[70,50]`으로 **80칸** 보고 (순간이동 분기).
```
[1] 순간이동 보고 후 — 방장이 본 게스트: gx:70 gz:50 trail:0  ← 칸은 옮겨졌는데 궤적 0
[2] 작은 걸음 8칸   — trail:8                                ← 평시 경로는 정상
[3] 집 복귀(88칸)   — cells:25 → 25,  trail:8 그대로 남음     ← 점령 실패
```

### (2) 수정 후 — 같은 시나리오
```
[1] 순간이동 보고 후 — gx:70 gz:50 trail:1                   ← 그 칸이 찍힌다
[2] 작은 걸음 8칸   — trail:9
[3] 집 복귀(88칸)   — cells:25 → 34,  trail:0                ← 점령된다
    격자 궤적 칸수  방장 {2:9, 3:28, 4:28} / 게스트 {2:9, 3:28, 4:28}   ← 완전 일치
```

| 판정 | 수정 전 | 수정 후 |
| --- | --- | --- |
| 순간이동 보고에 궤적 생김 | **False** (0칸) | **True** (1칸) |
| 작은 이동으로 궤적 자람 | True (8칸) | True (9칸) |
| 집 복귀 시 점령됨 | **False** (25 → 25) | **True** (25 → 34) |
| 궤적 비워짐(점령 완료) | **False** (8칸 잔류) | **True** |
| 방장·게스트 땅/좌표 동일 | — | **True** |
| 격자 궤적 칸수 동일 | — | **True** |

### (3) 리스폰 후에도 같은가 — 지시 추가점검 ①
옛 궤적을 가로질러 죽인 뒤(자기 궤적 규칙 정상 작동, 12칸에서 사망),
리스폰 → `warpT`(2초) 가 **타임아웃으로 풀린 뒤 첫 보고가 또 64칸을 넘는** 경우를 만들었다.
```
리스폰 완료 — gx:153 gz:48 cells:25 alive:true
리스폰 후 순간이동 보고 — 궤적 1칸 (자리 70,90)        ← 빠지지 않는다
리스폰 후 집 복귀      — 방장 32칸 / 게스트 32칸, 궤적 0 ← 점령된다
```
**`applyInput()`의 `warpT` 분기와 충돌하지 않는다.** 둘은 순서가 다른 일을 한다 —
`warpT`는 "이 보고를 **받을지**"를 고르고(`dd > 3`이면 버린다), 이번 수정은 "받은 보고가
멀 때 **그 칸을 어떻게 처리할지**"를 고친다. `respawnEnt()`가 `ent.gx/gz`를 리스폰 칸으로
세워 두므로 `dd` 계산의 기준도 유효하다. 수정 전에는 이 경로에서 칸이 조용히 사라졌고,
수정 후에는 리스폰 자리에서 끊긴 채 새 칸부터 다시 긋는다 — 없는 선을 긋지 않는다.

### (4) 게스트 예측 셀이 남지 않는가 — 지시 추가점검 ②
모든 회차에서 **게스트 잔여 예측 셀 0**이었다. 어긋나지 않는 이유는 세 겹이다.
- `markPred()`가 **확정이 있거나 내 땅인 칸은 건너뛴다** (`pred[i] || trail[i] || owner[i] === me.id`).
- `applyState()`가 확정 셀(`d.c`)에 `pred[i] = 0`을 찍는다. `predCell[]` 색인은 남지만
  `dropPred()`가 `!pred[i]`면 바로 빠져나오므로 두 번 지우는 일이 없다.
- 확정이 안 오는 예측은 `PRED_TTL`(1500ms)로 걷힌다. `clearPred()`는 사망·리스폰 때 전부 지운다.

> 수정 전에 게스트 **자기 화면**에서 벌어진 일도 이걸로 설명된다. `predictTrail()`도 자체
> 순간이동 분기가 있어 새 칸 하나만 미리 깔아 두는데, 방장이 그 칸을 확정해 주지 않으니
> 1.5초 뒤 TTL로 사라졌다. **내 선이 한 칸 떴다가 없어지는** 그림이었다.

### (5) 3인 (게스트 2) — 1회

```
방 인원 3 (사람 3 + 봇 1) — 위 (2)·(3)의 모든 판정 True 동일
격자 궤적 칸수 방장 {2:9, 4:27} / 게스트 {2:9, 4:27}
```

```
봇 자멸 0회 · 피살 30회 · 점령 484회 · 아이템 197개 · 스킬 160회
```

## 감독 확인 요청 / 남은 이슈
1. **직접 방 만들어 둘이 붙어 보고, 참가 직후 첫 이동부터 선이 그려지는지.**
   예전에는 멀리서 들어온 첫 보고가 조용히 버려졌다.
2. **64칸 문턱 자체는 그대로 뒀다.** 이 값은 "여기까지는 이어 붙이고, 넘으면 끊는다"는 선이고
   이번 버그와는 무관하다. 다만 격자가 200칸이라 **정상 플레이 중 지연으로 64칸이 넘으면
   그 구간은 이어지지 않고 끊긴다**(궤적에 구멍 → 폐곡선이 안 닫힘). 지금은 끊긴 자리에서
   새로 긋기 때문에 점령 실패로는 안 가지만, 지연이 심한 회선에서 선이 토막날 수 있다.
   문턱을 올릴지(이어 붙이는 범위를 넓힐지) 판단 필요하다.
3. 25 문서의 남은 판단 네 건(공격성 수준 · 확장 성향 사망률 · 저격수 집계 · 성향 숨김)은 그대로다.
